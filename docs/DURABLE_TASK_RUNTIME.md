# Durable Agent Task Runtime

Issue #45 adds a small coordination runtime above Bridge's existing batch execution plane. It does not replace GitHub as engineering truth. The public surface keeps the five execution/evidence tools and adds one fenced lifecycle tool, `bridge.task_transition`.

## Authority and non-goals

The runtime grants exclusive mutation authority for one bounded stage of one explicitly enrolled task. It does not plan across unrelated Issues, choose product priorities, persist chat transcripts, keep dirty workspaces alive, or interpret source code in the Watchdog.

For an enrolled task:

- GitHub is durable engineering truth: repository, primary Issue, canonical branch, exact SHAs, PR/CI, stage checkpoints and durable decisions.
- D1 is ephemeral coordination truth: dispatch, lease/fencing, active run pointer and latest checkpoint pointer.
- A Worker is disposable. Conversation identity is not task identity.
- Canonical task mutation/publication must use the governed Bridge path and a current lease epoch.
- Existing Bridge target/policy SHA and stale-base checks remain mandatory.

## Task identity and durable GitHub state

The durable task key is:

```text
owner/repository#issue-number
```

Every enrolled task has exactly one canonical product branch unless an explicit durable state change migrates it.

The canonical current-state pointer is compact navigation state, not a second journal:

```yaml
task: owner/repo#267
mode: continuous
status: ready
canonical_branch: agent/p06-s5
checkpoint:
  stage: S5.5
  sha: <exact-sha>
  comment: 123456789
blocker: null | { reason, comment }
next_stage: S5.6
continuation: same-worker | handoff | null
pr: 269
```

Stage/evidence history remains append-only Issue comments. Lease heartbeats and other runtime churn do not belong in GitHub comments.

## Coordination schema

The initial D1 schema is one row per task:

```sql
CREATE TABLE agent_tasks (
  task_key TEXT PRIMARY KEY,
  repository TEXT NOT NULL,
  issue_number INTEGER NOT NULL,
  canonical_branch TEXT NOT NULL,

  mode TEXT NOT NULL CHECK (mode IN ('supervised', 'continuous')),
  status TEXT NOT NULL CHECK (
    status IN ('READY', 'DISPATCHING', 'RECOVERING', 'RUNNING', 'ORPHANED', 'BLOCKED', 'DONE')
  ),

  dispatch_id TEXT,
  dispatch_expires_at TEXT,

  lease_owner TEXT,
  lease_epoch INTEGER NOT NULL DEFAULT 0,
  lease_expires_at TEXT,

  active_run_id TEXT,

  checkpoint_sha TEXT,
  state_comment_id INTEGER,

  last_transition_reason TEXT,
  updated_at TEXT NOT NULL
);
```

D1 does not retain an unbounded task event history. If the coordination row is lost, durable task identity and progress must be reconstructable from GitHub.

## State machine

Normal path:

```text
READY
  -> DISPATCHING
  -> RECOVERING
  -> RUNNING
  -> READY | BLOCKED | DONE
```

Failure/takeover path:

```text
RUNNING
  -> ORPHANED
  -> DISPATCHING
  -> RECOVERING
  -> RUNNING
```

Required transition rules:

- Only READY or ORPHANED may atomically create a dispatch.
- DISPATCHING is bound to one unexpired dispatch ID.
- Only the holder of that dispatch may activate a Worker.
- Activation atomically increments `lease_epoch` and assigns `lease_owner`.
- A stage may mutate canonical task state only while its lease is current and unexpired.
- A stale epoch never regains authority, even if the old Worker resumes.
- BLOCKED and DONE never auto-dispatch.
- Expired DISPATCHING becomes dispatchable again.
- Expired RUNNING/RECOVERING without a live bound Bridge Run becomes ORPHANED.
- A QUEUED/RUNNING bound Bridge Run is execution-aware liveness and suppresses takeover; it renews the associated lease and every still-live task-session capability for the same owner/epoch.

## Dispatch identity

`dispatch_id` is a single-use activation capability generated by the server-side task runtime.

Conceptual operation:

```text
task_tick / dispatch(task_key)
READY|ORPHANED -> DISPATCHING
dispatch_id = unique opaque id
dispatch_expires_at = bounded expiry
```

Compare-and-set semantics guarantee duplicate watchdog ticks have one winner. A crashed launcher cannot hold a task forever because the dispatch expires.

## Stage lease and fencing

The exclusive unit is a bounded engineering stage, not a chat session.

Activation/claim:

```text
claim(task_key, worker_id, dispatch_id)
lease_epoch = prior_epoch + 1
lease_owner = worker_id
lease_expires_at = bounded expiry
status = RECOVERING
```

`lease_epoch` is the fencing token. Every task-aware Bridge Run/publication binds:

- task key;
- lease epoch;
- canonical branch;
- exact base SHA;
- run/request identity.

Before task-bound mutation/publication, Bridge checks the current task row. A mismatched or expired epoch fails closed with a stable task-runtime error. This is additive to existing policy/target/stale-base validation.


## Canonical mutation enforcement contract

Task fencing is enforced inside Bridge at two independent boundaries:

1. before a task-aware Run is durably dispatched, the current task lease and epoch are checked and the resulting Run ID is CAS-bound to that lease;
2. before an edit/batch candidate is published, Bridge reloads the durable Run request and revalidates the bound task lease/epoch. A stale epoch fails with `TASK_LEASE_STALE` before Bridge creates a publish ref or dispatches the publish workflow.

The public MCP surface does not accept model-supplied task identity. `taskKey`, `workerId` and `leaseEpoch` remain server-owned runtime identity.

For cloud-hosted MCP workers, task-aware `bridge.run`, `bridge.get_run`, `bridge.get_result`, `bridge.publish` and `bridge.task_transition` accept only the opaque short-lived `taskSessionToken` issued by activation. Bridge resolves that token server-side to the authoritative task/worker/epoch mapping and then reuses the existing D1 fencing checks.

Successful task-bound token-authenticated operations use sliding expiry: Bridge proves that the token, operation identity, and same owner/epoch lease are current, then transactionally extends the lease and token to the same bounded expiry. Invalid or unrelated traffic does not renew ownership, and an already expired token or lease is never revived. Durable-task Run polling and evidence retrieval therefore include the token, and the Watchdog should tick a bound active Run before expiry so long execution cannot leave a still-live token behind while renewing coordination state.

For programmable clients that can control MCP HTTP headers, the existing three-header task-session transport remains supported as a compatibility path.

The canonical branch and exact base SHA are derived from the resolved target and persisted in the durable request.

For a **hard single-writer guarantee**, an enrolled canonical task branch must not remain directly writable through an independent credential path. Repository deployment must enforce one of these equivalent controls:

- a GitHub ruleset/branch-protection rule that restricts writes to the Bridge publication authority; or
- an organizational repository-write policy that makes Bridge the only credential path able to mutate the enrolled canonical branch.

Direct owner/admin writes remain an explicit break-glass operation and must first block/unenroll the durable task. Prompt instructions such as "do not push" are not a concurrency control.

Stable fencing failures are:

- `TASK_RUNTIME_UNAVAILABLE` — a task-aware request reached a transport without the durable task runtime;
- `TASK_BINDING_INVALID` — the persisted task/run binding is malformed or contradicts the exact Run target;
- `TASK_BINDING_MISMATCH` — enrolled repository/canonical branch no longer matches the Run binding;
- `TASK_LEASE_STALE` — lease owner/epoch/expiry/status no longer grants the stage authority.

## Recovery-before-mutate

After activation, a Worker must recover before editing:

1. read task state and primary Issue;
2. read the latest durable checkpoint;
3. resolve the canonical branch;
4. resolve exact current HEAD;
5. compare checkpoint SHA to HEAD;
6. inspect intervening commits/diff;
7. inspect relevant PR/CI/prior Bridge result when necessary;
8. read repository-local governance;
9. determine current/next bounded stage;
10. mutate only after reconciliation.

If checkpoint is A and canonical HEAD is D, valid already-pushed A..D work is recovered and reused. A fresh Worker does not create `branch-v2` merely to avoid reconciliation.

## Durable GitHub state and recovery implementation

The primary Issue contains one managed current-state block delimited by:

```text
<!-- bridge-durable-task-state:v1:start -->
... fenced JSON ...
<!-- bridge-durable-task-state:v1:end -->
```

Human-authored Issue content outside that block is preserved. Stage checkpoints are append-only Issue comments marked with `bridge-stage-checkpoint:v1`. Production reconciliation accepts machine checkpoint/blocker comments only from the verified GitHub user bound to the enrolled Bridge principal; marker text from other commenters is not authority.

Recovery deliberately reads both:

- the compact current-state block; and
- the latest machine checkpoint comment.

This makes the checkpoint path resilient to a crash after the comment is created but before the Issue-body pointer is updated.

Normal resume never creates a branch. It resolves the recorded canonical branch and exact HEAD. If the checkpoint SHA differs from HEAD, recovery calls GitHub compare and accepts only a complete linear descendant history whose merge base is the checkpoint. The Worker receives the intervening commits/files for inspection. Divergence, truncated compare evidence, a changed canonical branch, or an irreconcilable HEAD fails closed.

The crash-after-push-before-checkpoint case is therefore:

```text
checkpoint A
canonical branch HEAD D
recovery => inspect complete A..D
           reuse valid already-pushed work
           do not create branch-v2
```

Checkpoint creation verifies that the supplied SHA equals the current canonical branch HEAD, appends the durable checkpoint comment first, and then advances the managed current-state pointer.

## Execution modes

### supervised

```text
recover -> claim stage -> execute -> verify -> checkpoint -> release -> stop/report
```

A new explicit continuation is required for the next stage.

### continuous

```text
recover -> claim stage -> execute -> verify -> checkpoint -> release
-> if next stage is already durably authorized and no hard stop exists:
     obtain a new valid stage claim and continue
-> else stop
```

A checkpoint boundary is always a persistence/verification boundary; it is not inherently a human-approval boundary.

## Deterministic Watchdog decision

The Watchdog implementation consumes only the current coordination row and, when present, the exact bound Bridge Run state.

Decision order:

```text
BLOCKED | DONE
  -> NOOP

READY | ORPHANED
  -> atomic dispatch CAS
  -> one DISPATCH winner

DISPATCHING + unexpired dispatch
  -> NOOP

DISPATCHING + expired dispatch
  -> atomic replacement dispatch CAS

RECOVERING | RUNNING + task-bound Bridge Run QUEUED/RUNNING
  -> renew same epoch lease by CAS
  -> extend still-live same-owner/epoch task-session capabilities to that expiry
  -> NOOP

RECOVERING | RUNNING + valid stage lease
  -> NOOP

RECOVERING | RUNNING + expired lease + no live bound Run
  -> ORPHANED by current-epoch CAS
  -> atomic dispatch CAS
```

The Watchdog does not inspect source files, commit recency, Issue prose, diffs or test semantics. A live Bridge Run is execution-aware liveness even when no commit has occurred recently. If an `active_run_id` resolves to a Run whose task key, epoch or canonical branch does not match the coordination row, the Watchdog fails closed with `TASK_ACTIVE_RUN_MISMATCH` rather than guessing that takeover is safe.

## Watchdog and launcher contract

The Watchdog is deterministic. It asks only whether a task needs a Worker:

```text
task_tick(task_key) -> NOOP | DISPATCH
```

It does not read source code, choose branches, infer engineering progress, or mutate repositories.

The Launcher only launches:

```text
launch({
  taskKey,
  dispatchId,
  bootstrap,
  workerProfile
}) -> launcher receipt
```

The bootstrap contains durable pointers, not narrative implementation state.

## Production task control and scheduling

The Cloudflare deployment keeps operator task control outside the six public MCP tools.

Internal/operator control endpoint:

```text
POST /task-runtime/control
Authorization: Bearer <BRIDGE_TASK_RUNTIME_ADMIN_TOKEN>
```

Supported actions are intentionally small:

```text
enroll
inspect
tick
```

Enrollment is explicit and binds one durable task to the existing Bridge principal whose repository grant already allows `run` and `publish`. The task key must exactly match `repository#issue`. This adds only an authorization pointer (`bridge_user_id`) to D1; GitHub remains the engineering journal.

`tick` resolves the owning principal, reuses existing repository authorization/GitHub App credentials for read-only Run liveness, and then invokes the deterministic Watchdog. It does not inspect source code or Issue prose.

Cloudflare Cron invokes `tickAll` every five minutes. The cadence is deployment infrastructure, not task protocol semantics. If `BRIDGE_TASK_LAUNCHER_URL` is not configured, the scheduled handler returns a safe skip and creates no unattended dispatches.

When a launcher URL is configured, a DISPATCH result is passed to the existing `DurableTaskLaunchCoordinator`; duplicate launch prevention remains the D1 `launch_id` CAS from T6.

New deployment-only settings:

```text
BRIDGE_TASK_RUNTIME_ADMIN_TOKEN   secret, >= 32 chars
BRIDGE_TASK_LAUNCHER_URL          optional HTTPS endpoint
BRIDGE_TASK_LAUNCHER_TOKEN        optional launcher bearer secret
```

These values never appear in MCP tool schemas, GitHub durable task state, launcher bootstrap, or evidence.

## Worker Launcher implementation

The runtime uses a narrow launcher adapter:

```text
launch({
  taskKey,
  dispatchId,
  bootstrap,
  workerProfile?
}) -> bounded launcher receipt
```

`DurableTaskLaunchCoordinator` first claims the current dispatch in D1. The CAS writes one `launch_id`; only the winner may invoke the external launcher. This prevents duplicate Watchdog/launcher deliveries from starting two Workers for one dispatch.

The initial programmable adapter is `HttpWorkerLauncher`. It POSTs only:

- task key;
- dispatch id;
- standard recovery bootstrap;
- optional worker profile.

It does not receive repository credentials. Deployment-specific launcher authentication may be supplied as HTTP headers from deployment secrets. A Codex app-server/SDK adapter or another worker runtime can sit behind this HTTPS endpoint without changing Task Runtime semantics.

The dispatch expiry is also the activation deadline. If the external launcher call is ambiguous (for example, a network failure after request delivery), Bridge records `LAUNCH_UNKNOWN` and does not retry the same dispatch. The dispatch is allowed to expire; a future Watchdog tick creates a new dispatch, and the old dispatch can no longer activate a Worker.

`ManualWorkerLauncher` is the fallback. It returns the exact standard bootstrap and dispatch pointer for a human-started Worker while preserving the same activation/fencing rules.

The standard bootstrap contains only durable pointers and generic recovery instructions. It must not carry current file names, failing tests, narrative handoff state, or repository credentials.

## Programmable Worker activation and MCP session binding

The production Cloudflare composition exposes five execution/evidence tools plus the bounded `bridge.task_transition` lifecycle tool. Task-session transport is split by client capability: cloud-hosted MCP workers carry the opaque `taskSessionToken` in task-aware `bridge.run` / `bridge.publish` / `bridge.task_transition` arguments, while programmable clients may carry the server-owned task pointers in MCP HTTP headers.

A launched programmable Worker activates exactly one dispatch with:

```text
POST /task-runtime/activate
{
  "taskKey": "owner/repo#267",
  "dispatchId": "dispatch-..."
}
```

The dispatch ID is a short-lived, single-use activation capability created by the atomic Watchdog dispatch. It is delivered only through the Worker launcher bootstrap. Activation generates a fresh server-owned random Worker identity and consumes the dispatch through the existing D1 activation CAS.

The activation response contains no GitHub credential. It returns the current lease/session pointers plus an opaque short-lived cloud capability:

```text
task key
worker owner identity
lease epoch / expiry
canonical branch
execution mode
taskSessionToken
three MCP session headers
```

### Cloud-hosted MCP path

OpenAI-hosted/ChatGPT MCP workers should use the opaque capability:

```text
bridge.run(..., taskSessionToken)
bridge.publish(runId, taskSessionToken)
bridge.task_transition(..., taskSessionToken)
```

The model does **not** send `taskKey`, `workerId` or `leaseEpoch` as tool arguments. Bridge resolves the token to the authoritative runtime identity and verifies:

- authenticated Bridge principal owns the enrolled task;
- token is current and unexpired;
- task/worker/epoch mapping is current;
- repository/canonical branch/base binding still matches.

Only the token digest and minimum mapping are persisted; the raw token exists only as ephemeral activation material.

### Programmable header transport

Clients that control MCP HTTP headers may instead send:

```text
x-bridge-task-key
x-bridge-task-epoch
x-bridge-task-owner
```

All three headers must be present together.

The token and header transports are **task-session pointers/capabilities, not repository authority**. The OAuth-protected MCP request must still authenticate a Bridge principal, and every repository operation still passes the principal-scoped repository grant and GitHub App installation checks. The task key must also resolve to the same repository as the Bridge Run target. Ordinary non-task MCP calls use neither transport.

For a task-aware request Bridge creates a request-scoped Gateway with:

```text
taskContext = task key + epoch
taskLeaseValidator = current epoch + current Worker owner
```

Both Run submission and publication therefore require:

```text
valid OAuth principal/repository grant
AND
current task lease epoch
AND
current Worker owner
AND
canonical branch
AND
exact base SHA
```

A stale epoch or wrong Worker owner fails closed. The Worker owner value is ephemeral coordination authority: do not write it to GitHub Issue comments, source code, launcher receipts intended for humans, or ordinary logs.

The activation endpoint is intentionally not an MCP tool. Watchdog, Launcher, enrollment and activation remain internal/operator coordination. The sixth public tool is only the current Worker's fenced stage transition; it cannot dispatch, activate or enroll a task.

## Continuous Worker loop implementation

`DurableTaskWorkerLoop` is a thin orchestration layer over existing components. It does not plan engineering work and does not add an execution engine.

Activation:

```text
dispatch
-> D1 activate / epoch++
-> GitHub durable recovery
-> verify mode + canonical branch agreement
-> Worker inspects checkpoint -> HEAD evidence
```

A bounded stage is supplied by the Worker/harness as ordered #39 batch steps. The loop forcibly binds:

```text
repository = durable task repository
targetRef = canonical branch
targetSha = recovered exact HEAD
taskContext = task key + current lease epoch
mode = batch
```

The execution path remains:

```text
bridge.run(batch)
-> bridge.get_run
-> bridge.get_result
-> VERIFIED ? bridge.publish(runId) : require SUCCEEDED/no edit
-> revalidate current lease
-> GitHub durable checkpoint
-> bridge.task_transition
-> D1 completeStage / release lease
```

If recovery found linear work after the previous checkpoint, the Worker must explicitly acknowledge that it reviewed/adopted the recovered commits/files before any new mutation.

A stale Worker cannot write a checkpoint: checkpointing is preceded by a fresh lease/fencing validation. If publication succeeds but the Worker loses authority or dies before checkpoint, GitHub HEAD remains ahead of the previous checkpoint and T4 recovery adopts that work.

For `supervised`, the Worker stops after the durable checkpoint.

For `continuous`, after checkpoint + release it may CAS-claim the already-authorized next stage. The next claim increments `lease_epoch`. The Watchdog may race the same READY state; if the Watchdog/another Worker wins, the current Worker stops rather than bypassing ownership.

For a cloud Worker, a continuous claim is usable only after the rotated task-session token is persisted. If token issuance fails, Bridge uses the exact new epoch + owner + checkpoint CAS to release that unstarted claim back to READY immediately; it never decrements or reuses the fencing epoch.

Execution/evidence failure and explicit Hard Stops append a durable GitHub blocker first, update the managed state with its exact reason/comment pointer, then transition D1 to BLOCKED and release mutation authority. Bridge dereferences that exact blocker comment before accepting the transition.

If a Worker fails after persisting GitHub state but before `bridge.task_transition`, the Watchdog does not guess on ordinary polls. Only after the current lease expires and no bound Run is live, it performs one bounded GitHub reconciliation event. The exact checkpoint comment, current canonical HEAD and forward ancestry are verified before an advanced READY/DONE checkpoint is adopted; a durable BLOCKED state is also reconciled. If a status-bearing checkpoint or blocker comment was written but the Issue pointer update was interrupted, the newest exact machine event can complete recovery. Unchanged GitHub state is treated as a crash: the lease becomes ORPHANED and the task is redispatched. Regressed checkpoint pointers or task/branch/mode divergence fail closed. A late Worker cannot transition after expiry.

## Hard stops

Continuous execution stops and persists BLOCKED when:

- canonical branch/HEAD cannot be reconciled;
- unrelated or unexplained diff exists;
- another valid owner exists;
- repository governance/authority is unclear;
- settled architecture would need reopening without new durable evidence;
- a security/governance boundary would need weakening;
- destructive migration, secrets or new production authority is required;
- work crosses into an independent unauthorized Issue/stage;
- evidence cannot support the transition;
- a product decision genuinely requires a human.

## Security invariants

- Task enrollment is explicit.
- Existing principal/repository authorization remains authoritative.
- Candidate code cannot grant itself task-runtime authority.
- Canonical task mutation/publication cannot bypass fencing.
- Stale epochs fail closed.
- Existing exact target/policy SHA and stale-base protections remain in force.
- Watchdog is not an arbitrary executor.
- Launcher receives no unnecessary repository credentials.
- No permanent high-privilege shell or GitHub credential is introduced.

